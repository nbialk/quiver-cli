# Quiver V2: Why It Changed and How to Upgrade

V2 separates finding an entry, choosing its source, and updating its content.
Quiver manages those operations without keeping a bundled copy of every external
skill or adding another agent runtime.

**For existing projects, `migrate` changes lockfile metadata only. It does not
update skill files, switch their sources, or make legacy entries automatically
updatable.** Source assignment is a separate, explicit decision.

## Release Highlights

- External skills install and update directly from their original GitHub
  repositories, independently of the Quiver catalog and CLI release cycle.
- Custom skills, curated variants, commands, plugins and MCP definitions live in
  the separate [quiver-catalog](https://github.com/nbialk/quiver-catalog).
- Installed entries have independent source baselines and, for GitHub sources,
  exact commit pins. A changed catalog pointer cannot redirect an installation.
- `sync` only generates local provider output. Normal `check` no longer accepts
  local changes or records MCP snapshots implicitly.
- Explicit migration preserves V1 content and customizations instead of guessing
  where they came from or replacing them with the latest upstream version.

## Why the Source Model Changed

V1 compared installed content with the configured catalog. Matching the catalog
was useful, but it did not establish whether the original author had published
something newer. With the default bundled catalog, the update path was:

```text
Author repository -> catalog copy -> CLI release -> project
```

Even a scheduled catalog sync could not guarantee freshness: imports still had
to succeed, be reviewed and merged, and reach a CLI release. V1 supported remote
catalogs too, which avoided the package-release step, but external skills still
depended on the catalog's copies.

V2 removes that intermediate copy for external skills:

```text
External skill:  author repository -> locked project copy
Custom content:  catalog repository -> locked project copy
```

The catalog still provides convenient names and selection metadata. It is no
longer the authority for the contents of an unchanged third-party skill. That
also removes the need to release a new CLI just to make a skill update available.

There is a trade-off: direct upstream updates are not necessarily reviewed by
the Quiver maintainer. A recorded repository, commit and digest make the selected
snapshot explicit; they do not certify authorship, quality or safety. Updates
remain a deliberate user action, not a background process.

## What the Catalog Does Now

| Content | Authoritative source | Catalog's role |
| --- | --- | --- |
| External skills, such as shadcn | Original repository | Optional name and source pointer |
| Own skills, such as cleanup | Maintained catalog repository | Content and discovery |
| Curated variants, such as posthog-custom | Maintained catalog repository or an explicit fork | Clearly identified custom content |
| Commands, plugins and MCP definitions | Selected catalog repository | Content and discovery |

For a new project, `quiver-cli add shadcn` resolves the default catalog's pointer
and downloads the skill from its original repository. You can skip catalog
lookup entirely with a direct source:

```bash
quiver-cli add github:shadcn-ui/ui/skills/shadcn
```

Once installed, its own source in `quiver.lock` controls updates. Removing or
retargeting the catalog alias does not change that source. Updating just one entry
does not advance the pins of other entries.

An MCP source pin covers its configuration, not the deployed server or its live
tool list. A plugin pin covers the selected adapter and definition, not a
separately installed executable such as RTK.

## What Stays the Same

The runtime source of truth remains the committed `.agents/` content and
`quiver.lock`. Claude Code, OpenCode and Codex still consume native local files.
Provider output is generated and gitignored, not linked to a download cache.

No network access is required to regenerate provider output from a complete
checkout. Project-owned guides, provider overlays and local MCP enable/disable
settings are not silently replaced by a skill update. Accepted local edits also
remain protected: accepting a local baseline never changes the pristine source
baseline used to guard future updates.

## Breaking Changes

V2 changes persisted state and command behavior, not just where downloads come
from. Review scripts and CI invocations as well as interactive usage.

| V1 behavior or command | V2 behavior or replacement |
| --- | --- |
| One catalog descriptor controlled entry updates | Each installed entry has its own source; the catalog descriptor is for discovery |
| V1 lockfile writes | Run `migrate` before commands that change the lockfile |
| Bundled catalog and package-relative `local:` paths | Separate remote catalog; local development catalogs require an absolute path |
| `upstream` and `upstream pull` | Removed; use `update --dry-run` and `update` for installed entries with assigned sources |
| `sync` refreshed local digest baselines | Only regenerates provider output; accept reviewed local changes explicitly |
| Normal `check` could record snapshots and metadata | Project-read-only, including the first MCP observation |
| `check --accept` without a target | Use `check <id> --accept` or deliberately select `check --all --accept` |
| `sync --providers=opencode,claude` | Use `providers opencode,claude` |
| `--yes` / `-y` selected everything | Confirms defaults only; `--all` explicitly selects everything |
| Non-interactive `init` implicitly selected everything | Requires `--empty` or an explicit `--all`; `init --force` cannot replace an existing lockfile |
| No command defaulted to initialization | Shows help; invoke `init` explicitly |

Unknown, extra and command-inappropriate arguments now fail rather than being
ignored. Value flags still require `=`, for example `--providers=opencode`.
`add` without an argument opens a picker only in an interactive terminal.

Machine-readable output also distinguishes incomplete checks from successful
observations. Inspect both `ok` and `complete` in `check --json`: an intentional
offline skip can pass local checks without verifying live MCP tools. An update
preview may exit successfully when updates are available; blocked legacy entries,
local changes or source errors produce a nonzero exit code. Do not interpret a
failed or skipped lookup as "up to date."

## Upgrading an Existing Project

The following commands require `quiver-cli` 2.0.0 or later. Check `quiver-cli help`
for `migrate`; a released V1 executable does not implement these commands. A new
project starts with a V2 lockfile through `init` and does not need migration.

### 1. Inspect and Preserve the Current State

Run these in the repository you are upgrading:

```bash
git status --short
quiver-cli list
quiver-cli check --offline --json
```

Keep a recoverable copy of your current `.agents/` and `quiver.lock`, using your
normal version-control or backup workflow. Preserve uncommitted customizations
too. Investigate unexpected missing files or drift before approving replacements.
Do not accept every baseline merely to silence a failed check.

V2 can read a V1 installation for `list`, `sync` and normal `check` without
fetching its historical catalog. An offline check is not an upstream freshness
check or a verification of live MCP tools.

### 2. Migrate Metadata Only

```bash
quiver-cli migrate --dry-run --json
quiver-cli migrate
git diff -- quiver.lock
```

The dry run writes nothing. Migration changes the lockfile schema, including
renaming the installed location field from `sourcePath` to `installedPath` and
preserving historical catalog information under each entry's `legacy` source.
Installed files, IDs, paths, accepted local digests and MCP snapshots stay intact.
Running `migrate` again on a V2 lockfile does not rewrite it.

**Expect entries to remain `legacy`.** V1 metadata cannot reliably prove which
original repository revision produced every installed file. An old global catalog
commit or upstream import baseline is not sufficient evidence. Migration therefore
does not invent a source digest or guess a GitHub revision. `update`, even with
`--force`, will not update a legacy entry without an explicit source.

### 3. Review and Assign Sources Individually

For an existing `skill:shadcn` that you want to track from the original repository:

```bash
quiver-cli update skill:shadcn --source=github:shadcn-ui/ui/skills/shadcn --dry-run --json
```

This fetches a candidate without modifying project files; it may populate the
download cache. Inspect the proposed repository, path, ref and commit in
`reports[].to`, together with `contentChanged` and the entry's status.

| Preview result | Next action |
| --- | --- |
| `updated` with `contentChanged: false` | If this is the intended source, remove `--dry-run` to bind it without replacing local files |
| `local-changes` | Keep the current files and review the differences; source assignment has not been applied |
| `error` | Resolve missing/unsafe content, unavailable sources, invalid paths or authentication before trying again |

For legacy entries, different bytes do not necessarily mean you edited them:
Quiver cannot distinguish an older unmodified copy from a local or curated
variant. It preserves both rather than guessing.

The preview is a metadata summary, not a line-by-line diff. Compare the complete
installed directory at `installedPath` in `quiver.lock` with the proposed source
tree, including scripts and references. If they differ, retain the local variant,
maintain it in your own catalog or fork, or explicitly approve a replacement.
Only that last choice warrants `--force`, scoped to the reviewed entry. There is
no routine "force everything" migration step.

A dry run does not reserve a revision. A branch may move before the next command.
An explicit full commit SHA in `#ref` selects exactly that revision, but also
freezes future updates until you explicitly change the ref.

Use the source location appropriate to the installed entry type:

| Existing entry | Example source | Selected artifact |
| --- | --- | --- |
| `skill:cleanup` | `github:nbialk/quiver-catalog/skills/code/cleanup` | Complete skill directory |
| `command:review` | `github:nbialk/quiver-catalog/commands/review.md` | Command file |
| `mcp:context7` | `github:nbialk/quiver-catalog` | Named definition in the catalog's `config.json` |
| `plugin:rtk` | `github:nbialk/quiver-catalog` | Named plugin definition and its adapter file |

These are examples for entries already installed under those IDs, not instructions
to assign every installation to the default catalog. Team-owned catalogs and
absolute `local:/path/to/artifact` sources remain valid explicit choices.

The V1 PostHog skill was a curated combination, not an unchanged upstream copy.
If you want the maintained Quiver variant, review the candidate under
`github:nbialk/quiver-catalog/skills/integrations/posthog-custom`, not an assumed
equivalent in the original PostHog repository. Binding a new source preserves the
existing installed ID and path; it does not rename `skill:posthog` automatically.

Migration also preserves the old discovery catalog. If it still names
`local:template/.agents`, catalog-name and interactive additions cannot load that
removed bundled catalog. Use direct GitHub sources for new skill additions.
Assigning an existing entry's source does not reconfigure discovery; only fresh
initializations use the new default catalog automatically.

### 4. Verify the Result and Review MCP Baselines

```bash
quiver-cli sync
quiver-cli check --offline --json
git diff -- .agents quiver.lock .gitignore
```

Review and commit the intended local contents, lockfile and ignore rules with
your team. Keep generated provider files, `.env.local` and local overrides out
of the commit. Restart your provider when necessary to load changed configuration.

MCP snapshots preserved by migration do not need automatic reacceptance. With an
existing baseline, use a verbose check to review the reported changes and accept
a new snapshot only after deciding that those changes are legitimate:

```bash
quiver-cli check mcp:context7 --verbose
quiver-cli check mcp:context7 --accept
```

Without an existing baseline, `check` reports `missing-baseline`; even `--verbose`
does not display the complete candidate tool definitions. Review the server and
its exposed tools independently through your provider or an MCP client before
establishing the first baseline. The two commands above alone are not that review.

`--accept` performs a new observation; it does not save the result of the preceding
check, and live tools may have changed between calls. Inspect the recorded result
with `quiver-cli inspect context7`. Stdio introspection additionally requires
`--introspect-stdio`, which authorizes running the configured process.
If a changed MCP configuration is accepted without a successful new observation,
its old tool snapshot is cleared rather than reused for the new configuration.

### 5. Use the Separate Daily Operations

```bash
quiver-cli update --dry-run --json
quiver-cli update skill:shadcn
quiver-cli check --offline
quiver-cli sync
```

`update` checks assigned sources, `check` checks local integrity and optionally
live MCP observations, and `sync` regenerates derived output. An accepted local
customization still blocks automatic replacement because the pristine source
digest remains separate from the accepted local digest.

## Limits and Safety

- GitHub is the only remote source host in V2. Git LFS hydration and submodule
  checkout are not implemented; symlinks inside a selected skill are unsupported.
- A branch or named tag follows that exact ref. There is no semver-range or
  automatic latest-tag selection. An unrelated repository commit is not a skill
  content update, and a fixed full-SHA ref stays fixed even with `--force`.
- Downloaded skill scripts are copied, not executed by Quiver. Provider agents
  may execute them later. Review source changes before enabling them.
- Updates are applied per entry, not as one global or crash-atomic transaction.
  Successful entries remain locked if another fails. Check all report statuses;
  use `sync` to repair failed provider generation and retain any reported recovery
  backups until you have reviewed them.
- `sync` and `check --offline` do not contact sources or the CLI update notifier.
  An offline success only describes the local checks that actually ran.
